# Learning: 実装理解の補完

Claudeが実装した内容を振り返り、ユーザーが理解できていない部分を洗い出して**その場で解説**する。
ユーザーが希望したポイントについてのみ、後から実践資料を生成する。

**起動方法**: ユーザーが **`/learning` コマンドを明示的に実行したとき** に起動する。自動発火はしない（コーディングが一段落したタイミングで、ユーザー自身が `/learning` を叩く運用）。

**実践資料の出力先**: `../claude-learning/[ジャンル]/[トピック名]/`

ジャンル一覧:
| フォルダ名 | 対象 |
|---|---|
| `algorithm` | アルゴリズム・データ構造 |
| `database` | ORM・SQL・テーブル設計・マイグレーション |
| `language` | 言語構文・型システム（TS generics, async/await など） |
| `framework` | フレームワーク固有機能（Next.js App Router, React hooks など） |
| `library` | 個別ライブラリ（Zod, Stripe, date-fns など） |
| `architecture` | 設計パターン（DDD, MVC, SOLID, Clean Architecture など） |

---

## Phase 0: 起動

**Goal**: 学習セッションを開始する

**重要**: `/learning` を呼び出した時点でユーザーには学習意図がある。
「分からない部分はありますか？（なければスキップ）」のような**自己申告で終了させる質問はしない**。
ユーザーが「わかったつもり」になっている箇所こそ洗い出す対象なので、自己申告に委ねてはいけない。

**Actions**:
1. 「学習セッションを始めます」と一言伝え、即座に Phase 1 に進む。
2. ユーザーへの確認や離脱の問いかけはせず、Claude が対象範囲（Phase 1〜2）を選出し、
   その重要ポイントそれぞれについて Phase 3 でユーザー自身に説明させる。
3. （ユーザーが明示的に「やめる」「中止」等と言った場合のみ中断する。それ以外は必ず Phase 3 まで進める）

---

## Phase 1: 実装内容の把握

**Goal**: 今回Claudeが実装した内容を特定する

**Actions**:
1. 引数（`$ARGUMENTS`）があれば対象ブランチ/コミットとして使う
2. なければ現在のブランチの直近コミットを確認する
   ```bash
   git log --oneline -10
   git diff HEAD~1..HEAD --name-only
   ```
3. 変更されたファイルを実際に読んで実装パターン・使われた技術を把握する

---

## Phase 2: 学習トピックの抽出

**Goal**: 理解度チェックの対象トピックをリストアップする

**Actions**:
1. 実装内容から以下の観点で学習候補を検出する:
   - 新しく使われたライブラリ・API・Hook
   - 非自明なロジック・アルゴリズム
   - 設計パターン（状態管理・非同期処理・Context・カスタムHooks など）
   - 複雑な型定義・ジェネリクス
   - DB操作・クエリ・トランザクション
   - 認証・セキュリティ周り
2. 候補を重要度順に最大5件に絞る
3. 各トピックについて「ジャンル」「トピック名（英語ケバブケース）」「1〜2文のやさしい説明」を用意する

---

## Phase 3: インタビュー（理解度チェック）

**Goal**: ユーザーが理解できていない部分を特定する

**最重要原則：はい/いいえで聞かない**
「理解できていますか？」と自己申告で聞くと、本人も気づかない思い込み（わかったつもり）を見抜けない。代わりに **そのトピックの核心となる特定のポイントについて、ユーザー自身の言葉で説明させる**。返ってきた説明を読んで、Claude が理解度を判定する。

**Rules**:
- トピックを **1つずつ** 提示し、ユーザーの回答（説明）を待ってから次に進む
- 各トピックにつき **核心を突く問いを1つ**だけ投げる。問いは以下を満たすこと:
  - 「はい/いいえ」や単語1つでは答えられない（説明を要する）
  - **暗記やコード再掲では答えられず、仕組みを理解していないと説明できない**（なぜそう書くのか / どういう順で何が起きるのか / もし〜だったらどうなるか、など）
  - そのトピックの「ここを外すと理解したとは言えない」中心概念を狙う
- ユーザーの説明を読み、下記**判定基準**で `理解OK` / `部分的` / `理解不足` に分類する
- ユーザーが「わからない」「説明できない」と答えた場合は `理解不足` とし、追い詰めない
- 判定後、**一言だけフィードバック**を返してから次のトピックへ進む:
  - `理解OK` → 簡潔に正しさを認め、説明に足りない補足が1点あれば添える
  - `部分的` / `理解不足` → 否定せず「ここは後で解説しよう」と前向きに繋ぐ（この場では長く講義しない。詳しい解説は Phase 4 で行う）
- `部分的` と `理解不足` を **Phase 4 の解説対象** に追加する
- 全トピックが `理解OK` なら Phase 4・5 をスキップし、「理解は十分でした」と伝えて終了する

**判定基準（rubric）**:
| 判定 | 目安 |
|---|---|
| `理解OK` | 核心の仕組み・理由を自分の言葉で説明できている。用語が多少不正確でも本質を捉えていればOK |
| `部分的` | 結論や使い方は言えるが「なぜ」「内部で何が起きるか」が曖昧、または一部に誤解がある |
| `理解不足` | 説明できない／コードの再掲や言い換えに留まる／明確な誤解がある |

判定は**説明の内容**で行うこと。「たぶん」「自信ない」といった態度表現に引きずられず、説明そのものが本質を捉えているかで判断する。

**質問フォーマット**:
```
📌 トピック X/Y: [トピック名]（[ジャンル]）

[実装コードの該当箇所を1ブロック引用]

質問: [核心を突く1問。例:「ここで `useEffect` の依存配列を空にすると、
再レンダリングのたびに何が起きる／起きない？ なぜ？」]

→ あなたの言葉で説明してみてください（うまく言えなければ「わからない」でOK）
```

## Phase 4: ターミナル上での解説とフォローアップ

**Goal**: 理解が不十分だったポイントを、その場（ターミナル）で1つずつ解消する。
**いきなり学習用フォルダに資料を書き出さない。まずは会話で解決する。**

対象は Phase 3 で `部分的` / `理解不足` と判定したトピックのみ（`理解OK` は対象外）。
これらを **1トピックずつ順番に** 次の流れで扱う。

**各トピックの流れ**:
1. **即座に解説する**: そのトピックの核心（なぜそう書くのか / 内部で何が起きるか / どこを誤解していたか）を、
   実装コードを引用しながらターミナル上で分かりやすく解説する。長すぎず要点を押さえる。図（ASCII）が有効なら使う。
2. **質問に答える**: ユーザーから質問があれば答える。納得が得られるまでやり取りする。質問がなければ次へ。
3. **実践演習の要否を聞く**: そのトピックのやり取りが一段落したら、こう尋ねる:
   ```
   このポイントについて、理解を定着させる実践演習を用意しますか？
   - ハンズオン（ゼロから段階的に組み立てる写経式チュートリアル。自分で書けるようになるのが主眼）
   - ドリル（ほぼ完成したコードの穴(TODO)だけを埋めて実行・自動検証する課題。核心だけ実践で固めるのが主眼）
   - 不要（解説だけでOK）
   ```
   - **ハンズオン or ドリルが希望された場合** = ユーザーは理論的理解に加えて**実践的な演習も求めている**ということ。
     そのトピックを「資料生成対象」として、希望された種類（ハンズオン / ドリル / 両方）とともに記録する。
   - 「不要」なら何も記録せず、次のトピックへ。
4. 次のトピックに進み、1〜3 を繰り返す。

全トピックのやり取りを終えたら Phase 5 へ。
**資料生成を希望されたトピックが1つもなければ、Phase 5 をスキップ**し「解説のみで完了」として終わる。

---

## Phase 5: 実践資料の生成（希望ぶんのみ）

**Goal**: Phase 4 で実践演習を希望されたトピックについてのみ、解説＋実践資料を生成する。

**出力先**: `../claude-learning/[ジャンル]/[トピック名]/`
**希望されなかったトピックは生成しない**（ターミナルの解説で完結している）。

各「希望ありトピック」について、以下を生成する:
- **`README.md`** … Phase 4 でターミナルで行った解説を、Q&Aでの補足も反映して文章化したもの（下記テンプレート）。
- **希望された種類に応じて、対応するものだけ**生成する:
  - ハンズオン希望 → **`handson/STEPS.md`**
  - ドリル希望 → **`mini-project/`**
  - 両方希望 → 両方
- チートシート等の追加ファイルは作らない（必要最小限に留める）。

---

### `README.md` ── 概念説明（解説の文章化）

```markdown
# [トピック名]

> ジャンル: [ジャンル] | 生成日: [YYYY-MM-DD]

## なぜ使うのか
[動機・解決したい問題を2〜3文で]

## どう動くのか
[仕組みの説明。図（ASCII）があれば添える]

## このプロジェクトでの使われ方
[実際のコードを引用して解説]

## つまずきポイント / Q&A
[Phase 4 のやり取りで出た疑問と回答を反映]

## まとめ
> [トピック名]とは: [一文の定義]
```

---

### `handson/STEPS.md` ── ステップ別ハンズオン（ハンズオン希望時）

**性質**: ゼロから段階的に積み上げる写経式チュートリアル。最小の出発点から少しずつ機能を足し、各ステップで穴埋め→完成コードを確認しながら、**自分で全体を組み立てて書けるようになる**のが主眼。実行は任意。

```markdown
# ハンズオン: [トピック名]を自分で書く

## 目標
[このハンズオンを終えると何ができるようになるか]

## Step 1: [最小の出発点]
**やること**: ...
**コード（穴埋め）**:
\`\`\`ts
// TODO: ここを実装してください
\`\`\`
**なぜそう書くか**: ...

<details>
<summary>完成コード</summary>

\`\`\`ts
// 答え
\`\`\`
</details>

## Step 2: ...
（繰り返し、3〜5ステップ）

## 完走チェック
- [ ] [確認ポイント1]
- [ ] [確認ポイント2]
```

### `mini-project/` ── ピンポイント実践ドリル（ドリル希望時）

**性質**: ほぼ完成したコードの `// TODO(あなた):` の穴（1〜3箇所）だけを埋めて**実行・自動検証**する課題。書く量は最小で、学習対象のコアだけに集中させ、**本番の文脈で核心を手を動かして固める**のが主眼。UI・配線・データは完成済みで提供する（「フロントもバックも0から全部書かせる」ことはしない）。

#### 最重要原則：忠実性（本番と同じ書き方）を最優先する
学習対象がフレームワーク/ライブラリ固有の書き方なら、**必ずそのフレームワークの実プロジェクトで練習させる**。CDN や疑似再現での「それっぽい再現」は**禁止**——本番と違う書き方を練習させてしまい逆効果になる。実行方式は学習対象の性質で2トラックに分ける：

| トラック | 対象 | 練習場 | 環境構築 |
|---|---|---|---|
| **① 実プロジェクト型** | framework / library / database / フレームワーク前提の architecture | 本物のスタックを scaffold してその中で練習 | **SETUP.md で手順を細かく指示** |
| **② 単体ファイル型** | 純粋な language / algorithm / 型・ロジック（フレームワーク非依存） | 依存ゼロの単一ファイル | 不要（実行コマンド一発） |

- 判断基準：**「本番でその概念を書くとき、フレームワークの構文・ファイル構成が必要か？」** 必要なら①、不要なら②。
- ②で十分なものを①にしない。①が必要なものを②/CDNで誤魔化さない。
- **言語・実行系はこのプロジェクトに合わせる**（例: Dart/Flutter プロジェクトなら ② は `solution.dart` を `dart run` で実行。Node 前提で書かない）。

#### 共通の鉄則
1. **ユーザーが書くのは `// TODO(あなた):` の箇所だけ**。原則 **1〜3箇所**に限定し、学習対象の概念に直接関係する部分のみ空ける。周辺コードは完成させておく。
2. 各 TODO には「ここで何の概念を試しているか」を1行コメントで添える。
3. 「まず動かす→TODOを埋める→期待結果を確認」で進められるようにする。検証コード（期待値との突き合わせ）を同梱し `✅/❌` を出す。

#### トラック①（実プロジェクト型）の作り方
`mini-project/` 直下に生成する：
- **`SETUP.md`** … 環境構築の手取り足取り手順（scaffold コマンド・`files/` のコピー先パス・起動コマンド・つまずきポイント）。
- **`files/`** … 練習用ファイル一式（本物のソース）。学習対象だけ `// TODO(あなた):` で空け、それ以外は完成済み。
- **`README.md`** … 概要・「書くのはTODOだけ」・期待結果・答え合わせ（下記テンプレート）。

#### トラック②（単体ファイル型）の作り方
`mini-project/` 直下に **`solution.<ext>`**（依存ゼロ・このプロジェクトの言語で動く、TODO以外は完成済み・検証コード同梱）と **`README.md`** を置く。

#### `mini-project/README.md` テンプレート
```markdown
# ピンポイント実践: [テーマ]

> 目安: [①30〜45分 / ②15〜30分] ／ あなたが書くのは [トピック名] の部分だけ

## これは何
[学習対象の概念]を**本番と同じ書き方**で実装して理解する課題。UI・データ・配線は用意済み。

## 環境構築・実行方法
（①）→ `SETUP.md` の手順どおりに練習プロジェクトを作って起動。
（②）→ 実行コマンド一発（セットアップ不要）。

## あなたが書く場所（ここだけ！）
- `[ファイル名]` の `// TODO(あなた):` …… [何を実装するかを1〜2文]
（その他のコードは完成済み。触らなくてよい）

## 進め方
1. まず**そのまま実行**して「動くが TODO 部分だけ未完成」の状態を見る
2. TODO を埋める
3. 再実行して「期待結果」になればクリア

## 期待結果
[埋めたあとに得られる画面・出力を具体的に]

## 答え合わせ
<details>
<summary>解答（TODO部分のみ）</summary>

\`\`\`
// 完成コード
\`\`\`
</details>
```

## Phase 6: 完了報告

**Goal**: セッションの結果を案内する

**Actions**:
1. 今回のやり取りを要約する（各トピックの判定と、解説で解消できたか）。
2. 資料を生成した場合は、生成したフォルダ・ファイルをツリー形式で表示する:
   ```
   ../claude-learning/
   └── [ジャンル]/
       └── [トピック名]/
           ├── README.md
           ├── handson/STEPS.md      ← ハンズオン希望時のみ
           └── mini-project/         ← ドリル希望時のみ
   ```
   - 実践資料の進め方（①SETUP.md / ②実行コマンド一発、「書くのは TODO だけ」）を一言添える。
3. 資料を1つも生成しなかった場合は、「解説のみで完了。必要になったら再度 `/learning` を」で締める。
4. 「次のコーディング前に一度読み返すと定着しやすいです」と伝える。
