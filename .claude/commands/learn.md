# Learning: 実装方針の選定 と 実装理解の補完

このスキルは **実装前** と **実装後** の2つのタイミングで使う（どちらに該当するかは Phase 0 が自動判定する）:

- **実装前（Phase 0-B）**: これから実装する内容について、まず**ユーザー自身が手法を提案**し、Claudeがそれを踏まえて他の適切な手法を比較提示する。ユーザーは自分の案とAIの案を比較して進め方を決めてから実装に入る。これにより、実装し終えてから「もっと良いやり方があった」と気づいて手戻りするのを防ぎ、ユーザー自身の手法の引き出しも広がる。
- **実装後（Phase 1〜5）**: Claudeが実装した内容を振り返り、**AIが先に**編集したコードの場所や関数を具体的に示しながら**その場で解説**する。起動時に変更点を**漏れなく棚卸し**し、そのうち重要なものを1つずつ解説する。ユーザーは解説を聞きながら自分の理解とすり合わせ、わからない点があればその場で質問する。重要ポイントの解説が済んだあとに**残りの変更点を提示**して、ユーザーが学びたいものを追加で選べるようにする（実装を急いで学習を後回しにしがちなユーザーの取りこぼし防止）。

実装前モードで方式が決まった場合は、実装完了後にユーザーが `/learn` を叩き直さなくても、そのまま実装後モードの Phase 1 に自動で接続する。

対象は2系統（主に実装後モードで使う分類）:
- **汎用知識**（アーキテクチャ・ライブラリ・構文・設計パターンなど）— プロジェクトを越えて再利用できる知識。解説後、自動的に学習ログとして`../claude-learning/`に蓄積する。
- **実装固有の理解**（今回編集した箇所の**データの流れ**と**コンポーネントの親子・依存関係**）— チーム開発で必須の「自分の変更が周囲とどう繋がっているか」を、ファイル名・関数名を挙げながらAIが具体的に解説する。プロジェクト固有の話なので**学習ログは作らない**（その場の解説で完結）。

**起動方法**: ユーザーが **`/learn` コマンドを明示的に実行したとき** に起動する。自動発火はしない。
- **これから何かを実装する場面**で叩けば、Phase 0-B（実装方針の選定）から始まる。
- **コーディングが一段落したタイミング**で叩けば、従来通り Phase 1（実装内容の把握）から始まる。
- どちらに該当するかはユーザーが意識する必要はなく、Phase 0 が自動判定する。

**学習ログの出力先**: `../claude-learning/[ジャンル]/[トピック名].md`（トピックごとに1ファイル。同じトピックを再び扱ったときはこのファイルに追記していく）
**索引**: `../claude-learning/INDEX.md`（全トピックの一覧。最終更新順）

ジャンル一覧:
| フォルダ名 | 対象 |
|---|---|
| `algorithm` | アルゴリズム・データ構造 |
| `database` | ORM・SQL・テーブル設計・マイグレーション |
| `language` | 言語構文・型システム（TS generics, async/await など） |
| `framework` | フレームワーク固有機能（Next.js App Router, React hooks など） |
| `library` | 個別ライブラリ（Zod, Stripe, date-fns など） |
| `architecture` | 設計パターン（DDD, MVC, SOLID, Clean Architecture など） |

## Phase 0: 起動（モード判定）

**Goal**: 「実装前（Phase 0-B）」か「実装後（Phase 1〜）」かを判定し、適切なフローに振り分ける。

**重要**: `/learn` を呼び出した時点でユーザーには学習意図がある。
「分からない部分はありますか？（なければスキップ）」のような**自己申告で終了させる質問はしない**。
ユーザーが「わかったつもり」になっている箇所こそ洗い出す対象なので、自己申告に委ねてはいけない。

**Actions**:
1. Phase 1 と同じ要領で、レビュー対象になりうる変更が存在するか確認する:
   ```bash
   git status --short
   git diff HEAD
   ```
   併せて `$ARGUMENTS` が実在するファイルパス／ディレクトリか、`git rev-parse --verify <arg>` が通るコミット／ブランチ名かを確認する。
2. **以下のいずれかに該当すれば「実装後モード」** と判定する:
   - `$ARGUMENTS` が実在するファイルパス／ディレクトリ、またはコミット／ブランチ名として解決できる
   - 未コミットの変更（`git status --short` の `??` 含む、または `git diff HEAD`）が存在する
   - 上記が無く、フォールバックとして直近コミットをレビュー対象にできる（Phase 1 の手順通り）
   → 該当すれば「学習セッションを始めます」と一言伝え、即座に **Phase 1** に進む。ユーザーへの確認や離脱の問いかけはせず、Claude が対象範囲（Phase 1〜2）を選出し、その重要ポイントそれぞれについて Phase 3 でClaudeが1つずつ解説する。
3. **いずれにも該当しなければ「実装前モード」** と判定する（＝レビューできる変更が無く、これから何かを実装しようとしている状態）。
   - `$ARGUMENTS` に実装したい内容の説明が入っていればそれを初期入力として使う。
   - 空であれば「これから何を実装しますか？」と端的に尋ねる。
   - **Phase 0-B（実装方針の選定）へ進む**。
4. （ユーザーが明示的に「やめる」「中止」等と言った場合のみ中断する。それ以外は必ず該当フローの最後まで進める）

## Phase 0-B: 実装方針の選定（実装前）

**Goal**: 実装に入る前に、ユーザー自身が提案した手法とClaudeが提案する手法を比較し、ユーザーが納得した上で実装方式を決める。**実装し終えてから「もっと良いやり方があった」と気づいて手戻りするのを防ぎ、ユーザー自身の手法の引き出しを広げる**のが狙い。

**最重要原則：必ずユーザーの提案から始める**
Claudeが先に手法を提示してはいけない。ユーザーが自分の頭で手法を考える機会そのものが学習になるため、**「人間からAIへの提案」を起点**にする。

**Actions**:
1. **ユーザーの提案を先に聞く**:
   - 実装したい内容を確認する（Phase 0 で `$ARGUMENTS` から得られていなければ質問する）。
   - 続けて「その実装、どんな方式で進めるつもりですか？あなた自身の案を教えてください」と尋ねる。
   - ユーザーが「特に案はない／わからない」と答えた場合のみ、この手順をスキップしてよい。その場合もステップ3の比較検討自体は必ずユーザーにさせる（Claudeが一方的に手法を決めない）。
2. **コードベースを調査する**: 関連する既存ファイル・実装パターン・使用ライブラリ・類似実装を実際に読んで把握する。当てずっぽうで手法を語らない。
3. **Claudeが手法を比較提示する**:
   - ユーザー案を踏まえた上で、他に適切と考えられる手法があれば1〜2案を追加提示する。ユーザー案が既に最良だと判断した場合は、無理に対抗案をひねり出さず、その理由を伝える。
   - 複数案がある場合は比較表で示す。観点の例（項目はケースに応じて増減してよい）:
     | 観点 | ユーザー案 | AI案A | AI案B |
     |---|---|---|---|
     | 実装コスト | | | |
     | 保守性・拡張性 | | | |
     | 既存コードとの整合性 | | | |
     | 学習効果（新しく学べること） | | | |
   - 「ユーザー案の強み／弱み」「AI案がなぜ有効か」を、一般論ではなく**このプロジェクトの実コード**に即して具体的に説明する。
4. **ユーザーに判断してもらう**: どの方式で進めるかはユーザー自身に選ばせる。ユーザーが推奨を求めた場合のみ、Claudeとしての推奨案とその理由を伝える（決定を代行しない）。
5. **合意した方式で実装に進む**: 通常のコーディングフローとして実装する。
6. **実装完了後、そのまま Phase 1 へ進む**: ユーザーが `/learn` を再度叩き直す必要はない。実装が一段落した時点で「実装が完了したので、続けて振り返りに入ります」と伝え、Phase 1（実装内容の把握）以降に自動で接続する。

## Phase 1: 実装内容の把握

**Goal**: 今回Claudeが実装した内容を特定する

**Actions**:

**対象範囲の決定（コミットは不要。実装直後そのまま `/learn` を叩ける）**:

1. **引数（`$ARGUMENTS`）がある場合** — その内容で対象を上書きする:
   - **ファイルパス／ディレクトリ**（例: `lib/i18n/`、`lib/common/db/task.dart`）→ そのパスに限定して対象にする
   - **コミットハッシュ／ブランチ名**（例: `abc123`、`develop`）→ そのコミット/ブランチとの差分を対象にする
   - 判別は実在チェックで行う（`git rev-parse --verify <arg>` が通ればコミット/ブランチ、ファイルとして存在すればパス）

2. **引数がない場合（デフォルト）** — **未コミットの変更（作業ツリー）** を対象にする。コミットしていなくてよい:
   ```bash
   git status --short        # 変更・未追跡ファイルの一覧
   git diff HEAD             # 追跡ファイルのステージ済み＋未ステージ差分
   ```
   - `git status --short` に出る未追跡ファイル（`??`）も新規実装として対象に含める。
   - **未コミットの変更が何もない場合のみ**、フォールバックとして直近コミットを使う:
     ```bash
     git log --oneline -10
     git diff HEAD~1..HEAD --name-only
     ```

3. 対象として特定したファイルを実際に読んで、実装パターン・使われた技術を把握する

**全変更点の棚卸し（完全リスト・取りこぼし防止の土台）**:

4. 対象範囲の中で、Claude（AIエージェント）が行った変更点を **漏れなく、かつなるべく細かい作業単位で** ポイント化し、内部の「全変更点リスト」として保持する。これは後で解説する重要ポイント（Phase 2 で選出）よりも**広い完全な一覧**で、実装を急いで学習を後回しにしがちなユーザーが、重要ポイント以外も取りこぼさず拾えるようにするためのもの。
   - 粒度の目安: 「1つの関数」「1つのロジック片」「1つの設計判断」など、**具体的な解説が1本作れる最小単位**で1項目にする。複数の関数・ファイルにまたがる変更を1項目に大きくまとめない（後の解説が抽象的・総論的になるのを防ぐため）。
   - 各項目に「短いラベル」と「1行で何を変えたか」を持たせる。
   - このリストは Phase 2 で一部が「解説する重要ポイント」に昇格し、**残り（未提示ポイント）は Phase 4.5 でユーザーに提示する**。ここでは提示せず、内部に保持するだけでよい。

## Phase 2: 学習トピックの抽出

**Goal**: Phase 3 でAIが解説する対象トピックを、**なるべく細かい作業単位**でリストアップする

トピックには **2つの種別** がある。両方を抽出対象にする。

| 種別 | 対象 | 学習ログ |
|---|---|---|
| **A: 汎用知識** | フレームワーク・ライブラリ・言語構文・設計パターンなど、プロジェクトを越えて通用する知識 | Phase 4 で自動的に記録する |
| **B: 実装固有の理解** | 今回編集した箇所の**データの流れ**と**コンポーネントの親子・依存関係**。このプロジェクト固有で、一般論ではない | **記録しない**（その場の解説で完結） |

**重要**: 後続の Phase 3 では、ユーザーに説明させるのではなく **AIが詳細かつ具体的に解説する**。1トピックが広すぎると解説が抽象的な総論になってしまうため、ここでの粒度が解説の質を決める。「〇〇機能を実装した」のような大きな塊で1トピックにせず、**「この関数」「このロジック片」単位**まで分解すること。

**Actions**:
1. **種別A（汎用知識）** を以下の観点で検出する:
   - 新しく使われたライブラリ・API・Hook
   - 非自明なロジック・アルゴリズム
   - 設計パターン（状態管理・非同期処理・Context・カスタムHooks など）
   - 複雑な型定義・ジェネリクス
   - DB操作・クエリ・トランザクション
   - 認証・セキュリティ周り
2. **種別B（実装固有の理解）** を以下の観点で検出する。チーム開発では、自分が触った箇所が周囲とどう繋がっているかを把握できていることが前提になるため、ここは必ず1件以上抽出する:
   - 編集したコードを通るデータの流れ（入力 → どこを経由して → どこへ出力／保存されるか）
   - 編集したコンポーネント／関数の親子・呼び出し関係（誰がこれを呼ぶか／これは何を呼ぶか）
   - ファイル／レイヤーをまたぐ依存（例: あるクライアントコンポーネントが、別ファイルで定義された関数・サーバー側の処理・グローバル状態・DAO などをどう使っているか）
   - 編集箇所を変えたときに影響が波及する範囲
3. Phase 1 の「全変更点リスト」から、候補を重要度順に並べる（種別A・B を合わせて。ただし種別Bを最低1件は含める）。目安として上位8件程度までを **Phase 3 で実際に解説する重要ポイント** とする。
   - ユーザーが自分で説明する負荷がない（AIが解説する）ぶん、旧フローより広めに扱ってよい。ただし1回に大量のトピックを詰め込みすぎるとユーザーが消化しきれないため、目安件数を超える分は無理に押し込まない。
   - **選ばれなかった残りの変更点は捨てずに保持する**（＝未提示ポイント）。Phase 4.5 でユーザーに提示し、希望されたら追加で学べるようにする。
4. 各トピックについて「種別（A/B）」「ジャンル」「トピック名（英語ケバブケース）」「1〜2文のやさしい説明」を用意する。種別Bのジャンルは便宜上 `data-flow` を使う。

## Phase 3: AIによる解説とQ&A

**Goal**: Claudeが編集した実コードの場所・関数を具体的に示しながら**先に解説**し、ユーザーが自分の理解とすり合わせて疑問点をその場で質問できるようにする。

**最重要原則：ユーザーに説明させない**
以前は「ユーザー自身の言葉で説明させ、Claudeが理解度を判定する」方式だったが、このスキルを使うのはエンジニア志望のユーザーであり、まず**AIが解説し、それをもとに自分の理解とすり合わせて足りない部分を自分から質問・調査する**方が実態に合う。自己申告や再現テストは行わない。

**この方式が機能するための前提（厳守）**:
- 解説は **Phase 2 で分解した細かい作業単位ごと** に行う。複数の変更点をまとめて総論的に語らない。
- 解説は **抽象論で終わらせず、必ず実際に編集したコードの場所（ファイルパス・関数名・行）を示しながら**、なぜそう書いたか／内部で何が起きるか／他のコードとどう繋がるかを具体的に説明する。「〜という機能を追加しました」で終わる解説は不可。
- **種別B（実装固有の理解）**は特に、データの流れ・呼び出し関係・影響範囲を、ファイル名・関数名を挙げて図解する。一般論の講義にしない。

**Rules**:
- トピックを **1つずつ** 提示し、そのトピックのやり取り（解説→Q&A）が終わってから次に進む
- 曖昧な自己申告確認（「理解できましたか？」等）はしない。かわりに解説の最後に必ず質問を受け付ける一言を添える

**各トピックの流れ**:
1. **AIが先に解説する**: 下記フォーマットで、実装コードを引用しながら詳細かつ具体的に解説する。図（ASCII）が有効なら使う。
   - **種別A（汎用知識）**: なぜそう書くのか / 内部で何が起きるか / このプロジェクトでどう使われているか。
   - **種別B（実装固有の理解）**: 今回のコードの繋がりそのもの。データの流れ（どこから来てどこへ行くか）、呼び出し・親子・依存関係、影響範囲を、ファイル名・関数名を具体的に挙げて図解する。
2. **質問を受け付ける**: 解説の最後に「ここまでで質問はありますか？（なければ『次へ』でOK）」と尋ね、ユーザーの応答を待つ。
   - 質問があれば、納得が得られるまでやり取りする（複数回のやり取りも可）。
   - 質問がなければ次のステップへ。
   - このやり取り（解説＋Q&A）は、後述の Phase 4 で**種別Aのトピックについて自動的に学習ログ化される**。ドリルやハンズオン教材は作らない（穴埋め演習をしたい場合はユーザーが自分で用意すればよいため、このスキルの対象外とする）。
3. 次のトピックに進み、1〜2 を繰り返す。

**解説フォーマット**:
```
📌 トピック X/Y: [トピック名]（[ジャンル]）

[実装コードの該当箇所を1ブロック引用（ファイルパス:行数 / 関数名を明記）]

解説:
- 何をしたか: [この作業単位で具体的に何を変更・追加したか]
- なぜそう書いたか: [設計判断・理由]
- 内部で何が起きるか / どう繋がるか: [処理の流れ、呼び出し元・呼び出し先、他ファイルとの関係]

→ ここまでで質問はありますか？（なければ「次へ」でOK）
```

全トピックのやり取りを終えたら Phase 4 へ。
**解説したトピックに種別Aが1つも無ければ、Phase 4 をスキップ**して Phase 4.5 へ進む（ログは作らない）。

## Phase 4: 学習ログの記録

**Goal**: このセッションでAIが実装した内容について、**どんな課題に対して・どう考えて・なぜその手法（特にライブラリやプラグインなど）を使ったのか**を、あとから振り返れる形でMarkdownに記録し、`../claude-learning/` に蓄積していく。

**方針転換の理由**: ハンズオンや穴埋めミニプロジェクトのようなドリル教材は生成しない。そうした演習はユーザーが必要に応じて自分で作れば十分であり、このスキルが本来担うべきなのは「実装の意思決定の記録」——同じ技術に再び出会ったときに過去の自分の判断を振り返れることだと考えるため。

**対象**: Phase 3 で解説した**種別A（汎用知識）のトピックのみ**。種別B（実装固有の理解）はこのプロジェクト固有の話でログとしての再利用価値が低いため対象外（Phase 3 のターミナル解説で完結させる）。
**ユーザーへの確認は不要**: 演習の要否のような選択制ではなく、種別Aとして解説したトピックは自動的にログ化する（低コストで蓄積すること自体に価値があるため）。

**ファイル構成（累積型）**:
- `../claude-learning/[ジャンル]/[トピック名].md` … **トピック（技術・手法）ごとに1ファイルを使い回す**。フォルダやハンズオン一式は作らない。同じ技術・パターンを別のセッションで再び扱ったときは、新しいファイルを作らず**このファイルに新しいエントリを追記**していく。これにより「このライブラリを自分は過去どう使ってきたか」が1ファイルに時系列で溜まっていく。
- `../claude-learning/INDEX.md` … 全トピックを一覧できる索引。ログを追記するたびに該当行を追加・更新し、**最終更新日が新しい順**に並べ替える。ざっと全体を見渡したいとき・他の人に共有するときの入口として機能させる。

**Actions**:
1. Phase 3 で解説した種別Aのトピックそれぞれについて、`../claude-learning/[ジャンル]/[トピック名].md` の存在を確認する。
2. **存在しない場合**: 下記テンプレートで新規作成する。
3. **既に存在する場合**: 冒頭のトピック説明はそのままに、`## 使用履歴` の下に新しいエントリを**先頭（最新が一番上）に**追記する。過去のエントリは書き換えない・消さない。
4. `../claude-learning/INDEX.md` を更新する（無ければ新規作成）。該当トピックの行を追加・更新し、最終更新日の新しい順に並べ替える。

### `[トピック名].md` テンプレート

```markdown
# [トピック名]

> ジャンル: [ジャンル]

## 使用履歴

### [YYYY-MM-DD] [そのセッションの実装テーマを一言で]
**課題**: [何を実装しようとしていたか。直面していた要件・問題]
**採用した手法**: [使用した技術・パターン・ライブラリ／プラグイン名]
**なぜこの手法か**: [検討した他の選択肢があればそれとの比較を含め、選んだ理由。Phase 0-B で手法比較をしたセッションなら、そこでの結論をここに反映する]
**実装箇所**: `path/to/file.ts` の `funcName()`（該当コードを1ブロック引用）
**学び・気づき**: [Phase 3 のQ&Aで深掘りした点、次回に活かせる教訓]
```

2回目以降にこのファイルへ追記する場合も、`## 使用履歴` の下に同じ形式のエントリを**新しい順で先頭に**追加する（`# [トピック名]` の説明部分は書き換えない）。

新しいログを追記するたびに該当行の最終更新日と一言サマリを更新し、テーブル全体を最終更新日の新しい順に並べ替える。

## Phase 4.5: 残りの変更点の提示と追加学習（取りこぼし防止ループ）

**Goal**: Phase 1 で棚卸しした「全変更点リスト」のうち、まだ解説していないポイントをユーザーに提示し、本人が学びたいものを追加で学べるようにする。実装を急いで学習を後回しにしがちなユーザーが、重要ポイント以外の取りこぼしを拾えるようにするための工程。

**Actions**:
1. これまで（Phase 3〜4、および本フェーズの過去ループ）で扱ったポイントを除き、Phase 1 の棚卸しリストに残っている**未提示ポイント**を一覧で提示する。提示フォーマット例:
   ```
   この変更には他にも次のポイントがあります。この中で学んでおきたいものはありますか？
   （番号で指定・複数可 / 「なし」で終了）
   1. [ラベル] — [1行説明]
   2. [ラベル] — [1行説明]
   ...
   ```
   - 未提示ポイントが1つも無ければ、この提示は省略して Phase 5 へ。
2. **ユーザーが番号（複数可）を指定した場合** — 指定された各ポイントについて、**そのポイントに対する Phase 3（AIによる解説とQ&A）から順に、Phase 3 → 4 のフローを繰り返す**:
   - まず Phase 2 の基準で種別（A/B）・ジャンルを判定し、Phase 3 のフォーマットでAIが解説してから質問を受け付ける。
   - 種別Aであれば Phase 4 と同じ手順で学習ログに追記する（出力先・テンプレートも同一）。
3. その回に指定されたポイントをすべて処理し終えたら、**手順1に戻り、まだ残っている未提示ポイントを再提示する**。ユーザーが「なし」「終了」等と言うか、未提示ポイントが尽きるまでこのループを続ける。
4. ユーザーが「なし」と答えた／未提示ポイントが尽きたら Phase 5 へ。

**注意**: この提示はあくまで選択肢の提供であり、全ポイントの学習を強制しない。ユーザーが「なし」を選べば、残りが未着手でもそのまま完了してよい。

## Phase 5: 完了報告

**Goal**: セッションの結果を案内する

**Actions**:
1. 今回のやり取りを要約する。Phase 1 の全変更点リストを基準に、「解説した重要ポイントとその中で出た質問」「Phase 4.5 で追加学習したポイント」「提示したが学ばずに残したポイント（未着手）」を区別して示す。
2. 学習ログを記録・更新した場合は、対象ファイルをツリー形式で表示する:
   ```
   ../claude-learning/
   ├── INDEX.md                      ← 更新
   └── [ジャンル]/
       └── [トピック名].md            ← 新規作成 or 追記
   ```
   - 新規作成したファイルと、既存ファイルに追記しただけのファイルを区別して示す。
3. 種別Aのトピックが1つも無く、学習ログを1件も記録しなかった場合は、「解説のみで完了。必要になったら再度 `/learn` を」で締める。
4. 「次のコーディング前に一度読み返すと定着しやすいです」と伝える。
