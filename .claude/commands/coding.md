# Coding Workflow

コーディング作業を始める前に現状を理解し、計画を立て、実装し、確認するまでを統一する。

## Phase 1: 作業内容の確認

**Goal**: 何をするのかを明確にする

**Actions**:
1. `.claude/TASKS.md` を読み込む
2. `$ARGUMENTS` が TASKS.md 内のタスク名またはキーワードと一致するか確認する
   - 一致する場合: そのタスクの「概要」「実装メモ」「参照ファイル」を作業内容として使う
   - 一致しない場合: `$ARGUMENTS` をそのまま作業内容として扱い、以降のフェーズを進める
3. 参照ファイルが指定されている場合はそのファイルも読んで詳細を把握する
4. 曖昧な点・未決事項があればユーザーに質問する
5. TodoリストをTodoWriteで作成する

**Note**: タスク完了後は `.claude/TASKS.md` の該当タスクのステータスを `[ ]` → `[x]` に更新する

---

## Phase 2: ブランチ・作業ディレクトリの作成

**Goal**: 最新の `develop` ブランチから新しいブランチと作業ディレクトリを作成する

**Actions**:
1. リモートの最新情報を取得する
   ```bash
   git fetch origin
   ```
2. 作業内容に合ったブランチ名を決める（例: `feature/add-product-filter`）
3. `origin/develop` ベースで worktree を作成する
   ```bash
   git worktree add -b <branch-name> ../<directory-name> origin/develop
   ```
   - 同名ブランチが既存の場合は `-b` を外してそのブランチをチェックアウトする
   ```bash
   git worktree add ../<directory-name> <branch-name>
   ```
4. `.env.local` が存在する場合は新しい作業ディレクトリにコピーする
   ```bash
   [ -f .env.local ] && cp .env.local ../<directory-name>/.env.local
   ```
5. 作業ディレクトリで依存パッケージをインストールする
   ```bash
   cd ../<directory-name> && npm install
   ```
6. 作成した作業ディレクトリで以降の作業を行う

**Note**: ブランチ名・ディレクトリ名は作業内容を端的に表す英語のケバブケースにする

---

## Phase 3: コードの理解

**Goal**: 関連ファイルを読んで既存のパターンを把握する

**Actions**:
1. 作業対象のファイルを読む
2. 関連するコンポーネント・スタイルを確認する
3. プロジェクトの命名規則・ディレクトリ構成を把握する

---

## Phase 4: 実装計画の提示

**Goal**: 変更方針をユーザーに確認してから進める

**Actions**:
1. 変更するファイルと変更内容を列挙する
2. ユーザーに提示して承認を得る
3. **ユーザーの承認なしに実装を開始しない**

---

## Phase 5: 実装

**Goal**: 計画通りにコードを書く

**Rules**:
- 既存のコードパターン・CSS変数に従う
- 作業範囲外のリファクタリングをしない
- コメントは必要最小限にする
- 完了したタスクをTodoWriteで都度チェックする

---

## Phase 6: 動作確認の要請

**Goal**: ユーザーに実際の動作を確認してもらう

**Actions**:
1. 作業ディレクトリで `npm run dev` を起動する
2. ユーザーに以下を伝える
   - 確認してほしいURL・画面
   - 確認してほしい操作・挙動
3. **ユーザーから「OK」または「問題あり」のフィードバックをもらうまで待機する**
4. 問題があれば Phase 5 に戻って修正する

---

## Phase 7: コミット

**Goal**: 規則に従ったコミットメッセージで変更を記録する

**コミットメッセージ規則:**

| プレフィックス | 用途 | 例 |
|------------|------|-----|
| `ADD:` | 新機能の追加 | `ADD: お気に入り登録・解除機能を追加（機能3）` |
| `FIX:` | バグ修正 | `FIX: 重複申請防止と売り切れ商品の検索除外` |
| `REFACTOR:` | 動作を変えないコード整理 | `REFACTOR: SellFormのhandleSubmitを分割` |
| `DOCS:` | ドキュメント・MD変更のみ | `DOCS: TASKS.mdの機能3ステータスを更新` |
| `STYLE:` | CSSのみの変更 | `STYLE: 商品カードのグリッドレイアウトを調整` |

**Note**:
- 本文にはTASKS.mdのタスク番号を含めると `check-progress` が自動判定しやすい（例: `機能3`）
- コミット後は `.claude/TASKS.md` の該当タスクを `[x]` に更新し `**完了コミット**: <hash>` を追記する

---

## Phase 8: 完了報告

**Goal**: 何をしたかを簡潔に伝える

**Actions**:
1. 変更したファイルと内容を箇条書きで報告する
2. 作成したブランチ名・作業ディレクトリを伝える
3. 残課題・注意点があれば伝える

---

## Phase 8: MDファイルの整合性チェック（自動）

**Goal**: 実装した内容を各MDファイルに反映し、記述の乖離を解消する

**Actions**:
1. Phase 7 の完了報告が終わったら、自動的に `/check-progress` スキルを起動する
2. 今回の実装で変更したブランチを対象として渡す
   - 例: `/check-progress <今回のブランチ名>`
3. check-progress スキルの Phase 3（差分検出）では、今回の実装に関連する乖離を優先的に検出する
4. check-progress スキルの Phase 4（確認）では、今回の変更に起因する修正は「確実なもの」として扱う

**Note**: このフェーズはスキップ不可。コーディング作業の締めとしてMDの整合性を常に保つ。

---

## Phase 9: 実装理解の補完（自動）

**Goal**: ユーザーが理解できていない部分を洗い出し、学習コンテンツを生成する

**Actions**:
1. Phase 8 が完了したら、自動的に `/learn` スキルを起動する
2. 今回実装したブランチ名を引数として渡す
   - 例: `/learn <今回のブランチ名>`
3. `/learn` の Phase 0（起動確認）でユーザーが「なし」と答えた場合はそのまま終了する

**Note**: このフェーズはスキップ不可。ただし `/learn` 内でユーザーが学習不要と答えれば即終了するので負担にはならない。
